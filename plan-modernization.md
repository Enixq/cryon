## Видение продукта

**Cryon — автономный кроссплатформенный музыкальный агрегатор:** одна локальная библиотека, один профиль вкуса и лучшая доступная версия композиции независимо от источника. Пользователь устанавливает приложение и начинает слушать музыку без Docker, VPS, домена или домашнего сервера.

> **Твоя музыка везде, с единым вкусом, единой библиотекой и лучшей доступной версией трека.**

## Границы продукта

- Не переносить Docker, Navidrome, VPS-туннель и обязательное скачивание библиотеки: это противоречит простому автономному запуску Cryon.
- Заимствовать продуктовые практики: качественный импорт, идентификацию композиций, фоновые задания, объяснимые рекомендации, здоровье источников и устойчивые сценарии библиотеки.
- LAN-режим возможен только как опциональное расширение: desktop открывает локальную библиотеку мобильному клиенту в одной сети после явного pairing.

## Реализованный первый срез (18 ноября 2026)

- Добавлен документированный HTTP API `/v1` рядом с legacy `/api/call`: health, источники, поиск, библиотека, плейлисты, фоновые задания и `playback/resolve`.
- Android-воспроизведение перенесено из WebView HTML5 audio в `Media3` `MediaSessionService`: сервис владеет звуком, notification/Bluetooth controls и 256 МБ LRU-кэшем потока; WebView получает только события состояния для переходного UI.
- Добавлены durable jobs в SQLite, воркер Go core, retry с backoff и API создания/отмены/наблюдения. Первый потребитель — пересканирование локальной библиотеки.
- Начата миграция React-клиента: standalone Android использует v1 для поиска, избранного и resolve потока; desktop может использовать тот же endpoint на origin Wails. Legacy RPC оставлен только для ещё не перенесённых экранов.

## Что сохраняем

- Go-адаптеры YouTube, SoundCloud, Яндекс Музыки, Spotify и локальных файлов.
- Локальную SQLite, историю, избранное, плейлисты, OAuth, lyrics и рекомендации.
- Единый Go domain core для desktop и Android.
- Автономные Windows и Android сборки без внешнего сервера.

## Корневые проблемы

- Android строится вокруг WebView + локального HTTP-сервера, а жизненный цикл плеера проходит через JavaScript bridge. UI не должен владеть воспроизведением.
- `internal/core.App` стал монолитом; reflection RPC делает транспорт неявным и не даёт типизированного контракта для новых клиентов.
- React-клиент одновременно знает Wails, HTTP, mock fallback и события.
- Отсутствуют durable jobs, единая идентичность трека и API-first контракты.
- Стабильность плеера, кэширование, fallback, диагностика и фоновые сценарии важнее новых рекомендаций, AI и большого количества экранов.

## Принципы архитектуры

1. **UI не владеет playback.** UI отправляет намерение и показывает состояние; platform player продолжает работу при фоне и recreation activity/window.
2. **Одна композиция, несколько вариантов воспроизведения.** Поиск, избранное, история и рекомендации работают с каноническим треком, а не с записью source.
3. **Сначала надёжность.** Playback state machine, retry, fallback, cache, логирование и диагностика важнее нового функционала.
4. **Контракт прежде клиента.** API v1 документирован и типизирован; Wails, Android и будущий LAN-клиент являются его клиентами.
5. **Долгие задачи не живут в UI.** Импорт, сканирование, обложки, кэш и рекомендации выполняются durable job queue с приоритетами и retry.

## Целевая архитектура

```text
Android Compose UI ──────┐       ┌── Android PlaybackService (Media3)
Desktop client UI ───────┼──────►│
                         │       └── Desktop PlaybackService (mpv adapter)
                         ▼
                 Cryon API v1 (typed HTTP + events)
                         ▼
             Go application services / domain core
                         ├── source adapters and stream resolver
                         ├── identity and candidate ranking
                         ├── recommendations and taste profiles
                         ├── durable job queue
                         └── SQLite with schema migrations
```

## Целевой стек

| Слой | Решение | Назначение |
| --- | --- | --- |
| Domain / integrations | Go | Сохранить адаптеры, стрим-resolve, SQLite и рекомендации |
| API | HTTP JSON API v1 + OpenAPI 3.1 + events | Типизированные модели и независимые клиенты |
| Android | Kotlin + Compose + Media3 / ExoPlayer | Нативный lifecycle, foreground playback, cache/offline |

| Desktop playback | Go `PlaybackService`, сначала bundled mpv | Заменяемый playback adapter |
| Local data | SQLite + versioned migrations | Надёжное обновление схемы |
| Background work | SQLite-backed job queue | Retry, priorities, progress и отмена |

## Почему не полный rewrite на Flutter, Rust/Tauri или Wails v3

- Go-core уже содержит ценную сложную логику и должен стать независимым сервисным слоем, а не быть переписанным ради смены языка.
- Tauri и Wails не избавляют Android от необходимости нативного Media3 service; WebView остаётся лишним посредником в критичном playback пути.
- Flutter остаётся резервным вариантом, но потребует полный React → Dart rewrite без решающего преимущества над Kotlin/Compose для Android media client.

### Правила выбора версии

- Предпочтения пользователя: local, original/explicit, official-only, quality, запрещённые источники.
- Ранжирование: confidence identity → explicit/original policy → длительность → качество → доступность → source priority.
- Плеер получает упорядоченный список кандидатов; при resolve/playback ошибке переключается на следующий и сохраняет причину в diagnostics.

## API v1

Reflection endpoint `/api/call` постепенно выводится из эксплуатации. Новый API явно группируется и документируется:

```text
/v1/search
/v1/catalog
/v1/library
/v1/playlists
/v1/imports
/v1/jobs
/v1/recommendations
/v1/playback
/v1/sources
/v1/system
/v1/events
```

### Реализовано в текущем этапе

- Desktop и mobile loopback-сервер отдают общий HTTP API v1 вместе с stream-proxy.
- React desktop использует v1 для поиска, избранного, истории, плейлистов, источников и рекомендаций; Wails RPC сохранён как compatibility fallback.
- Списки локальных треков и музыкальных папок также читаются через v1; системный выбор папки остаётся нативным для каждой платформы.
- Local library rescan запускается через persistent job queue, а UI показывает её состояние после recreation.
- Android playback вынесен в Media3 `MediaSessionService` с foreground lifecycle и 256 MB cache; WebView получает только состояние и команды.
- При ошибке потока Android запрашивает эквивалентную версию в другом сервисе, выбирает её по правилам identity/ranking, сохраняет текущую позицию и показывает пользователю причину переключения.
- Desktop делает то же самое для mpv и встроенного аудиоплеера: новая версия запускается с той же позиции, а не с начала композиции.
- В настройках появилась вкладка «Диагностика»: она хранит последние переключения и ошибки на устройстве и показывает источник, трек, причину и секунду продолжения.
- Desktop React routes загружаются лениво: стартовый bundle снижен с 538 KB до 414 KB до gzip.
- SQLite применяет схему только при переходе на новую версию; есть проверка, что более старая база корректно обновляется и восстанавливает таблицу фоновых задач.
- API v1 описывает состояние и команды desktop-плеера: старт, пауза, продолжение, остановка, перемотка и громкость. React сначала использует эти маршруты, а старый Wails-мост остаётся временным запасным вариантом.
- API v1 публикует поток событий `/v1/events`. Изменения источников, библиотеки, уведомлений и фоновых задач одновременно доходят до старого механизма и нового API, а Android HTTP-мост уже слушает новый поток.
- Пользователь может предпочесть локальную копию и настроить порядок сервисов при подборе прямой или запасной версии. Настройки explicit и официальности ожидают достоверных данных источников.
- Импорт избранного показывает отдельные итоги: найдено в источнике, реально добавлено в Cryon и уже существовало в библиотеке.

Контракт API включает DTO, error model, pagination, job/progress model и playback state model. OpenAPI является источником Kotlin/TypeScript-клиентов и контрактных тестов.

## Playback и мобильная стабильность

### Android

- Новый Kotlin `Media3` `MediaSessionService` является единственным владельцем playback, audio focus, Bluetooth/media buttons, notification и foreground lifecycle.
- Compose UI подписывается на состояние сервиса, а не управляет `<audio>`.
- Состояния: `idle`, `resolving`, `buffering`, `playing`, `paused`, `retrying`, `failed`, `ended`.
- Сохраняются queue, position, repeat/shuffle, кандидат источника и ошибка.
- Первый шаг offline: cache-first для текущего и следующего трека; затем управляемые offline downloads.

### Desktop

- UI общается с Go `PlaybackService` через API v1.
- mpv остаётся первой реализацией и поставляется с приложением; IPC и перезапуск изолированы внутри adapter-а.
- Контракт playback одинаков для desktop и Android, но движки не обязаны быть одинаковыми.

## Порядок реализации

1. **Stabilize:** tests, diagnostics, source health, playback failure evidence.
2. **Decouple:** service boundaries, migrations, typed API v1, compatibility adapter для текущего React/Wails клиента.
3. **Data foundation:** job queue, canonical tracks, matcher, candidates and fallback policy.
4. **Product:** imports, Mix of the Day, radio, feedback, local-library tools.
5. **Native mobile:** Compose + Media3 client на уже стабильном API.
6. **Desktop modernization:** сначала API migration, затем Compose Desktop при подтверждённой ценности общего UI stack.

## Критерии готовности

- Плеер продолжает воспроизведение при сворачивании Android UI и корректно восстанавливает очередь/позицию после перезапуска.
- Ошибка источника не выглядит как тишина: видны state, причина, retry и fallback result.
- Поиск не создаёт дубли одной композиции; пользователь видит выбранную версию и может изменить preference.
- Любая длительная операция отображает progress, переживает restart UI и имеет retry/cancel semantics.
- Новые платформенные клиенты создаются по OpenAPI без зависимости от Wails.
- `go test ./...` и frontend tests проходят в чистом окружении.
