# ВК Музыка: проверенные подходы и решение для Cryon

Исследование обновлено 25 ноября 2026 года.

## Выбранная реализация

Реализован один адаптер `internal/services/vkweb`: веб-сессия сайта ВК и
запросы самого веб-плеера через `al_audio.php` (`section`, `reload_audio`).
Методы `audio.*` и получение веб-токена удалены: в реальном аккаунте они
возвращали код 9 даже после паузы, тогда как сайт искал и играл музыку.
Основной пример протокола — NK Player. Python, Electron, Selenium и отдельный
ffmpeg для подключения не нужны.

На Windows Cryon открывает установленный Edge или Chrome с отдельным
временным профилем. Вход, QR, SMS и капчу обрабатывает сайт ВК. Через локальный
CDP-сокет читаются только cookies этого профиля с доменов ВК; обычные профили
пользователя не читаются. После получения сессии окно закрывается. Перед
сохранением Cryon открывает `/audio` и проверяет идентификатор пользователя,
включая аккаунт с пустой библиотекой. CookieJar сохраняет обновления cookies
при перенаправлениях через страницы входа; обновлённая сессия сохраняется.
Сессия сохраняется в `vk.webSession`, на Windows — через DPAPI текущего
пользователя. Токены музыкального API больше не запрашиваются.

На Android отдельная `VKVerificationActivity` открывает страницу ВК без
JavaScript-моста Cryon. CookieManager передаёт сессию локальному Go-серверу
с идентификатором текущей попытки. Сессия хранится в приватных данных приложения.

На Windows пользователь подтвердил реальный вход и воспроизведение новой
реализации. На Android обнаружено отличие: стандартный мобильный User-Agent
WebView отправлял `/audio` на `m.vk.ru`. Кроме того, прежний сборщик cookies
не включал сессию мобильного поддомена и завершал окно до окончания входа,
если находил старые cookies.
Теперь окно входа использует User-Agent обычного браузера с версией текущего
Chromium; Go нормализует ранее сохранённые мобильные User-Agent тем же способом.
Передача cookies ждёт распознанного UID на странице обычного веб-плеера,
учитывает `m.vk.ru`/`m.vk.com` и больше не требует `p` для действующего sid.
Ошибка проверки остаётся в окне с кнопкой повторной проверки вместо его закрытия.
На cookies телефона проверены обычная авторизация сайта, поиск и разрешение
ссылки через Go-адаптер на ПК; мобильный User-Agent возвращал ошибку сессии,
а User-Agent обычного браузера с теми же cookies дал 3 трека и ссылку MP3.
Сборка `vk-android-login-fix` установлена на телефон через ADB по Wi-Fi.
После обновления пользователь подтвердил успешный вход и реальное воспроизведение
на Android. Таким образом, вход и звук подтверждены пользователем на обеих платформах.

Поиск разбирает массивы аудиозаписей сайта, выбирает блок «Все треки»,
фильтрует короткие превью и явно ограниченные записи, удаляет повторы.
В идентификаторе трека сохраняются hashes для `reload_audio`, поэтому ссылку
можно обновить после перезапуска. Прямые ссылки из поиска используются без
дополнительного запроса; иначе `reload_audio` вызывается только при запуске трека.
Обфускация `audio_api_unavailable` декодируется с учётом UID пользователя.
Предпочтение отдаётся MP3/AAC; HLS определяется по `audio_streams`, в том числе
для URL без `.m3u8`. Для HTML5 используется лениво загружаемый hls.js; Media3
на Android и mpv на Windows сохраняют свои способы воспроизведения.
Плейлисты, сегменты и AES-ключи проходят через прокси Cryon с подписями,
привязанными к треку и сессии. Cookies ВК не отправляются на аудио-CDN.
Кэш прямых файлов отделён по сессии. Сохранение прямых файлов работает через
общий механизм Cryon; сохранение зашифрованного HLS пока отклоняется явно,
поскольку существующий Go-экспорт не преобразует MPEG-TS в аудиофайл.

Ошибки содержат этап (браузер, проверка сайта, поиск, трек), HTTP
статус или код веб-протокола; произвольные ответы сервера и секреты не попадают в сообщения.

Проверки: реальный установленный Edge/CDP с искусственными HttpOnly cookies,
Windows DPAPI, фикстуры сайта и обновления cookies, локальный HLS с AES-128 и Range,
переходы интерфейса входа, сборки Windows и Android. Пользователь подтвердил
вход, поиск и воспроизведение на Android; затем ВК начал отвечать кодом 9.
Диагностический поиск через сохранённую Windows-сессию получил код 9 как
через `api.vk.ru`, так и через `web.api.vk.ru`. Пользователь подтвердил, что
под тем же аккаунтом на сайте поиск и воспроизведение работают.
Веб-протокол вернул 20 записей в блоке «Найдено в тексте» и 3 в «Все треки»;
адаптер выбирает релевантный блок «Все треки». Проверка нового адаптера вернула
3 трека для Radiohead, разрешила ссылку MP3 и загрузила 65 536 байт аудио
с HTTP 206 и Content-Type `audio/mpeg`. Повторное получение ссылки использовало
кэш, новый экземпляр адаптера распознал экспортированную обновлённую сессию.
Это проверка сети и аудиоданных; полное прослушивание на устройстве остаётся
пользовательской проверкой.

## Исправление ограничения запросов и интерфейса

Поиск ждёт окончания ввода 650 мс и отменяет устаревшие HTTP-запросы.
Проверка ВК больше не запускает фоновый поиск. Адаптер разделяет одинаковые
запросы и кэширует поиск на 10 минут. Несколько обращений плеера используют
одну ссылку. Ссылка кэшируется до 50 минут
с учётом срока `expires` CDN (секунды или миллисекунды); пустой поиск — 30 секунд.
Новые запросы идут не чаще одного в 1,1 секунды, поиск — одного в 3 секунды.

Прежняя пауза на 15 минут не исправила отказ музыкального API и удалена
вместе с этим способом получения музыки. HTTP 429 самого сайта учитывает
Retry-After; при отсутствии заголовка применяется короткая пауза 30 секунд.
Существующие кэшированные ссылки доступны, сессия остаётся подключённой.
Веб-протокол также может иметь ограничения и изменяться; абсолютное отсутствие
отказов стороннего сервиса не гарантируется.

При выборе только ВК счётчик больше не включает плейлисты других сервисов.
Ошибки показываются прямо на странице поиска. Переход к настройкам ВК
восстановлен; сайт можно открыть без повторного подключения. На Android
«Сменить аккаунт» очищает только cookies доменов ВК перед новым входом.

## Почему прежние варианты удалены

Оба реализованных способа входа не прошли пользовательскую проверку:
старый `vkmauth`/`govkm` остановился после SMS, а Windows-модуль VKpyMusic
вернул общее сообщение «Не удалось получить ответ ВК Музыки».
В последнем модуле этим сообщением заканчивались как неизвестные ответы API,
так и ошибки сети, парсинга или выполнения Python. По одному сообщению нельзя
установить конкретную причину или утверждать, что неверны пароль или сеть.
Тесты с искусственными ответами и запуск встроенного Python проверяли код,
но не подтверждали вход в реальный аккаунт и доступ к полному аудио.

Из приложения удалены оба адаптера, обработчик входа, форма телефона/пароля,
капча/Selenium, Python-процесс, HLS-конвертация через VKpyMusic и её упаковка
в Windows CI. Удалены зависимости `govkm`, `vantuz` и `oauth2`, которые
использовались только этой интеграцией. Их код больше не используется новым
веб-адаптером.

Значение источника `vk` и его отображение в метаданных оставлены, чтобы ранее
сохранённые треки, история и данные синхронизации библиотеки продолжали читаться.
Прежние moosic/API-идентификаторы и `web_...` не отправляются веб-адаптеру;
такие онлайн-треки нужно найти заново. Сохранённые офлайн-файлы остаются доступны.
Новый формат — `site_<owner_id>_<audio_id>_<action_hash>_<url_hash>`.
Дисковый кэш поиска ВК имеет отдельную версию `vk-site-v1`, чтобы при обновлении
не возвращались старые `web_...` из шестичасовых снимков прежнего адаптера.

### vk-audio

Проверены версия 0.0.10 и ревизия
[`113cb12e`](https://github.com/ilyhalight/vk-audio/tree/113cb12e7470809eb0f9a09c96b7d0870c2575b5).
В [src/client.ts](https://github.com/ilyhalight/vk-audio/blob/113cb12e7470809eb0f9a09c96b7d0870c2575b5/src/client.ts)
`VKWebClient.refresh()` делает POST с cookies, Origin/Referer `vk.ru` и
`app_id=6287487`. В [src/index.ts](https://github.com/ilyhalight/vk-audio/blob/113cb12e7470809eb0f9a09c96b7d0870c2575b5/src/index.ts)
есть поиск `audio.search` и каталог. Тест авторизации требует действительных
cookies из окружения. Это подтверждает устройство реализации, а не её
работоспособность с аккаунтом пользователя Cryon.

Пример требует серверного или привилегированного HTTP-клиента: JavaScript
обычной страницы Cryon не может произвольно выставить заголовок Cookie для ВК.
Добавление npm-пакета в React не создаст эту возможность.

### NK Player

Проверены версия 1.6.1 и ревизия
[`d419a82a`](https://github.com/Gerasim00/NK-Player/tree/d419a82a5ca76a80ee24d9b35225274a89173261).
[main.js](https://github.com/Gerasim00/NK-Player/blob/d419a82a5ca76a80ee24d9b35225274a89173261/main.js)
открывает `https://vk.ru/login` в `WebContentsView`. Cookies принадлежат
браузерной сессии приложения. Для web API используется скрытое окно на
`vk.ru` и fetch с `credentials: 'include'`, затем `web.api.vk.ru/method/`.

[vk-audio.js](https://github.com/Gerasim00/NK-Player/blob/d419a82a5ca76a80ee24d9b35225274a89173261/vk-audio.js)
делает запросы к `al_audio.php` через `session.fetch`, разбирает внутренние
массивы ВК, получает ссылки через `reload_audio`, а также использует
`audio_streams`. Некоторые HLS-ссылки не содержат `.m3u8`; формат определяется
по метаданным потока. Это важное ограничение для будущего адаптера Cryon.
Веб-протокол остаётся внутренним и может изменяться.

### VK ID SDK

Изучены README и настройки SDK, а также официальная
[документация прав доступа](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/work-with-user-info/scopes).
В ней перечислены `vkid.personal_info`, `email` и `phone`. Общий способ
получить для собственного приложения Cryon доступ, эквивалентный
музыкальному клиенту ВК, в этих материалах не найден.

## Пользовательская проверка

Настройки → ВК Музыка → «Войти через сайт ВК». Завершить вход в отдельном
окне, дождаться проверки аудио, найти трек и прослушать полностью с перемоткой.
Повторить после перезапуска приложения. Если ВК отклонит запрос, интерфейс
покажет этап и доступный числовой код; это позволяет отличить отказ музыкального
протокола от сбоя входа на сайт. Тесты на фикстурах не заменяют эту проверку.
